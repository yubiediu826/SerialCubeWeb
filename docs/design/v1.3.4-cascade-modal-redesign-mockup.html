改动清单 (3 UX bug + 1 一致性 + 1 持久化 bug)

UX BUG
Title 重复 (协议/命令/卡片 都有): "确认删除命令 命令 0x01 Read Voltage?" — 当前代码用 `确认删除命令 ` 前缀 + label `命令 0x01 Read Voltage` 拼接, "命令" 出现 2 次。协议同样有 "确认删除协议 协议 proto_bms?" 重复。
修法: title 前缀改用类型, label 去掉前缀 (`0x01 Read Voltage` 不带 "命令" 前缀)。
UX BUG
"删除方式" section 是死的 + 双重选择机制矛盾 (命令/卡片): body "请选择" 暗示要选, 实际选择发生在底部 3 按钮 (仅删自己/级联/取消) — 用户会困惑。
修法: 删整个"删除方式"空 section + footer 3 按钮。命令/卡片只绑对应协议, 不存在跨协议级联, 不需要二选一 (跟协议删除对齐)。
一致性
协议/命令/卡片 删除 UX 不统一: - 协议删除: window.confirm() 原生弹窗 (无 modal 样式) - 命令/卡片删除: 3 按钮自定义 modal
修法: 3 modal 全部统一用新的简单 confirm 模式 (引用预览 chip + 蓝色信息条 + 2 按钮 [取消/确认删除])。
行为决策
自动级联 (3 个 modal 一致): - 删协议 → 自动删所有命令 + 引用这些命令的卡片 + 引用这些卡片的告警 - 删命令 → 自动删所有引用此命令的卡片 + 引用此命令的告警 - 删卡片 → 自动删所有引用此卡片的告警
理由: 引用关系只在协议内部有效, 引用方离开了被引用方就没意义, 留孤儿数据反而造成更多困惑。
UX 改进
「引用对象会一并删除」蓝色信息条: 引用预览 chip 下方加一行, 明确告诉用户会一并删除哪些 (如 8 条命令 + 12 张卡片 + 4 条告警)。无引用时显示 "无引用对象"。
持久化 BUG
命令/卡片删除刷新后会复活: SerialCube.html:14815 (命令删) 和 SerialCube.html:14913 (卡片删) 都没调 NS._saveUserConfig()。 协议删除 (line 14708) 调了, 切协议 (line 14461) 调了, 但命令/卡片 delete 漏了。
修法: splice 后加 NS._saveUserConfig && NS._saveUserConfig(); (跟协议删除对齐)。
保留
引用预览 chip 保留 (彩色分类: 命令蓝紫/卡片绿/告警红)。
