1现状问题 — 当前架构下，命令和协议为什么"看起来"只能一对一？

⚠ 根因不是 UI，是数据模型

当前 PROTOCOLS[] 只定义帧结构（header/addr/cmd/length/data/crc/tail 7 种字段），COMMANDS[] 是独立的全局数组，通过 cmd.protocol = 'proto_xxx' 字符串引用协议。

后果：

  • 协议编辑器只能展示"一条命令的帧预览"（previewCmd），其他命令看不到
  • 新建/编辑命令要去另一个 modal（"命令管理"），割裂
  • 删除协议时，引用它的命令成"孤儿"，靠 fallback 兜底（COMMANDS[0]）
  • 导入导出要分别维护 protocols 和 commands 两份数据，原子性差

24 个候选方案 — 你提的"协议簇"其实是另一个抽象，先对齐方向

不对题

A. 协议簇

你提的方案

把多个协议方案打包成"簇"（如 Modbus Suite = RTU + ASCII）。

proto_cluster_modbus ├─ proto_modbus_rtu └─ proto_modbus_ascii
适合：同一设备有多种传输层/变体
现状：我们用 8 种 kind（fixed-header/raw/cmd-split 等）已经覆盖变体场景
不对题：你问的是命令，不是协议变体
✓ 推荐

B. 命令清单挂在协议下

让命令成为协议的一等公民

每个 protocol 自带 commands[]，UI 上是协议编辑器的第 ② 段。

proto_bms { fields: [header, addr, length, data, crc, tail], // cmd 字段消失 commands: [ {id:0x01, name:'Read V', dir:'rx'}, {id:0x10, name:'Ctrl Chg', dir:'tx'}, {id:0x90, name:'Charge Ack', dir:'rx'} ] }
+ UI 和数据对齐
+ "命令管理" modal 退役
+ 导入导出原子化
- 迁移 cards 的 cmd 查询路径
过度设计

C. 命名命令集

跨协议复用命令

定义可命名的命令集（"BMS-Read-Set"），协议引用 set。适合多个协议共享同一组命令的场景。

set_bms_read = [0x01, 0x02, 0x03, 0x04] proto_bms.commands = set_bms_read proto_bms_v2.commands = set_bms_read
适合：多协议共享命令（现实里 5% 场景）
代价：多一层跳转（协议 → set → 命令）
判断：日常 95% 用不上，跳转打断编辑流
不对题

D. 子协议

协议父子层级

"Modbus" 是父协议，"Modbus-RTU" / "Modbus-ASCII" 是子协议。命令挂在叶子层。

modbus ├─ modbus_rtu { commands: [...] } └─ modbus_ascii { commands: [...] }
适合：协议变体需要继承公共属性
现状：我们没有"公共父协议共享字段"的需求
不对题：跟 A 一样，是协议层级问题不是命令问题

4迁移路径 — 老的 COMMANDS[] 数组怎么处理？

现状→方案 B 目标态
NS.COMMANDS 全局数组 → NS.PROTOCOLS[i].commands[] 嵌套数组
cmd.protocol = 'proto_xxx' 字符串引用 → 隐式归属 (父协议就是它的 protocol)
协议 fields[] 里的 cmd 字段 → 移除 (每条命令自带 id)
cards 用 card.cmd 查命令 → 用 NS.findCmd(cmdId) 跨所有协议查询
"命令管理"独立 modal → 退役 (编辑入口合到协议编辑器 ② 段)
导入配置 v1 格式 → 自动迁移 (按 cmd.protocol 归并到对应 proto)

兼容垫片: NS.allCommands() = PROTOCOLS.flatMap(p => p.commands || []) ，所有原本用 NS.COMMANDS 的地方改用这个 helper，零散点改动 ~15 处。
