# v1.3.4 — 3 个删除 modal 统一 + 编辑模式加固

> **发布日期**: 2026-08-14
> **触发原因**: 用户实测反馈 (1) 命令/卡片删除弹窗有 UX bug (title 重复 / 死 "删除方式" section / 双重选择机制矛盾) (2) 命令/卡片删除刷新后复活 (持久化漏调) (3) 编辑模式按钮 2x 触发 (单次点击弹 2 个 toast) (4) 编辑模式无需条件直接能进 (5) 编辑模式下删卡片也不持久化
> **影响范围**: 3 个删除 modal (协议/命令/卡片) + 编辑模式 toggle + 4 处卡片修改路径

---

## 1. 3 个删除 modal 完全统一

**v1.3.3 现状 (不一致)**:
- 协议删除 → `window.confirm()` 原生弹窗 (纯文本)
- 命令/卡片删除 → 3 按钮自定义 modal (取消 / 仅删自己 / 级联删除 N)

**v1.3.4 新设计 (统一)**:
- 协议/命令/卡片 删除全部用同一个自定义 modal
- Title: "确认删除 + label" (label 不带类型前缀, 避免 "确认删除命令 命令 0x01..." 这种重复)
- Body: 引用预览 chip + 蓝色信息条 "引用对象会一并删除: N 条命令 + M 张卡片 + K 条告警"
- Footer: 2 按钮 (取消 / 确认删除)
- 行为: 确认后自动级联 (引用方一并删, 跟协议删除 v1.3.3 一致)

**修的 3 个 UX bug**:
1. **Title 重复** — 旧代码用 `确认删除命令 ` 前缀 + label `命令 0x01 Read Voltage` 拼接, "命令" 出现 2 次。改为 label 去掉前缀 ("0x01 Read Voltage" 不带 "命令"), title 统一用 "确认删除 + label"。协议/命令/卡片 都修了 (之前都有类似重复, e.g. "确认删除协议 协议 proto_bms?")。
2. **"删除方式" section 是死的** — body 有 label + 描述 "请选择如何处理被引用的对象", 但下面没有任何 radio/checkbox 控件, 实际选择发生在底部 3 按钮, body 跟 footer 选择机制矛盾。删除整个死 section。
3. **双重选择机制矛盾** — 既然引用方离开被引用方就没意义 (命令/卡片只属其协议), 没必要 "仅删自己/级联" 二选一。删除行为简化为单一路径: 确认后自动级联, 引用方一并删。

**视觉小调整**:
- 橙色 "选'仅删自己'会留下孤儿" 提示条 改为 蓝色 "引用对象会一并删除: N 个" 信息条 — 橙色太抢眼跟主操作视觉冲突, 蓝色跟 modal 主题色一致更和谐
- 无引用时蓝色信息条变灰色态, 文字 "无引用对象, 仅删除当前项"

## 2. 持久化 bug 修复 (用户实测反馈命令/卡片删除刷新后复活)

**根因**: 命令/卡片删除 handler splice/filter 后漏调 `NS._saveUserConfig()`, 浏览器刷新被 `_loadUserConfig` + `_defaultProtocols()` / `_defaultCards` 默认值覆盖。

**修法**: 全部 modify 路径 splice/filter 后加 `NS._saveUserConfig && NS._saveUserConfig();`, 跟协议删除 (line 14710) + 切协议 (line 14463) 对齐。

**涉及的 7 处位置** (SerialCube.html):
| 位置 | 操作 |
|---|---|
| line 11623 (编辑模式 trend 卡片 del onclick) | `NS.CARDS = NS.CARDS.filter(...)` |
| line 11688 (编辑模式 list 卡片 data-action='del') | `NS.CARDS = NS.CARDS.filter(...)` |
| line 13865 (卡片编辑 modal 列表 del onclick) | `NS.CARDS = NS.CARDS.filter(...)` |
| line 14716 (协议删除 _openCascadeModal confirm 后) | `NS.PROTOCOLS/CARDS/ALERTS.filter(...)` (v1.3.3 已有) |
| line 14816 (命令删除 _openCascadeModal confirm 后) | `NS.CARDS/ALERTS.filter + proto.commands.splice(...)` |
| line 14933 (卡片删除 _openCascadeModal confirm 后) | `NS.ALERTS.filter + NS.CARDS.splice(...)` |
| line 16290/16298 (卡片编辑 modal 保存/删除) | `c.title/unit/type/cmd/field/range/precision = ...` / `NS.CARDS.filter(...)` |

## 3. edit mode 按钮 2x 触发 bug 修复

**用户反馈**: "点击模式直接弹窗两个弹窗, 进入编辑模式后又退出" — 单次点击编辑模式按钮, 弹 2 个 toast ("编辑模式: 可删除/添加/编辑卡片" + "已退出编辑模式"), 实际效果是进入后立刻退出。

**根因**: `NS.attachModalHandlers` 被调 2 次:
- L16469 脚本末尾: `window.__serialWebDashboard.attachModalHandlers();`
- L12659 `NS.start` 内部: `NS.attachModalHandlers();` (有 `!_initialized` 守卫, 但第一次 start 时也调, 等于调 2 次)

每次 `attachModalHandlers` 都执行 `bind('dh-toggle-edit', ...)` `addEventListener('click', ...)`, 重复绑定 → 单次 click 触发 handler 2 次 → 1st 进入编辑模式 (info toast), 2nd 退出编辑模式 (success toast), 净效果: 没变 + 2 个 toast。

**修法**: `attachModalHandlers` 入口加一次性守卫:
```js
if (NS._modalHandlersBound) return;
NS._modalHandlersBound = true;
```
`reset()` 同步清 flag (让 reset 后能重绑):
```js
NS._modalHandlersBound = false;
```

## 4. 编辑模式前置条件 (用户反馈)

**用户反馈**: "编辑模式的启用需要判断当前应用协议和启用串口没, 没连接串口就无法应用协议自然也无法编辑"

**修法**: `dh-toggle-edit` handler 入口加守卫 (line 16342-16354):
```js
if (!NS.editMode) {  // 只在"进入"时检查, 退出不受影响
  if (!NS._serialConnected) {
    NS.toast('请先连接串口 (编辑模式需基于已应用的协议)', 'warn');
    return;
  }
  if (!NS.activeProtoId) {
    NS.toast('请先在配置中心激活协议 (编辑模式需基于已应用的协议)', 'warn');
    return;
  }
}
```

## 5. _openCascadeModal API 简化

- 返回值: `'self' | 'cascade' | 'cancel'` → `'confirm' | 'cancel'` (移除 self 路径, auto-cascade 是唯一行为)

- 旧 `NS._cascadeConfirm` 保留兼容 (不删不调用), 旧 data-result="self" / "cascade" 元素已全部移除

## 8. Backlog (v1.3.5+)

- `_renderCascadeModal` meta 解析对协议用 `label.match(/0x.../)` 等正则, 不够健壮 (e.g. cmd 名字里如果有 0x 会误匹配)。建议改成传完整 cmd obj 给 renderer。
- 编辑模式图标尺寸 14x14 偏小, 用户反馈"未显示对应图标", 后续加大到 16 或 18。
- 协议删除的「确认删除 + 关联命令/卡片/告警会一并删除」文案可点击展开, 让用户看到具体哪些命令/卡片会被删 (现只显示数量)。
- 旧 `NS._cascadeConfirm` 兼容代码可清理 (v1.3.1 升级时为防回归保留的, 现在 v1.3.4 稳定后可以删了)。
