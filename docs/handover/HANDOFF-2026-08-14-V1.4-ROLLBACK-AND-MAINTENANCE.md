## 关键决策

### 1. 为什么 force-push 整个 main 链? (不 revert 12 commit)

用户选 A: "force-push 回 c4d8b08". 三方案对比:

| 方案 | 优点 | 缺点 | 决策 |
|---|---|---|---|
| **A. force-push main 到 c4d8b08** | 历史干净, v1.4.0 完全消失 | 改写共享历史 (私有仓库可接受) | **✓ 选这个** |
| B. revert 12 commit | 保留完整历史, 以后可 revert revert | main 链多 12 个 revert 噪音 | 不选 |
| C. 新建 archived-v1.4.0 分支 | 旧 main 改名保留 | semver 混乱, 旧 main 仍存在 | 不选 |

理由: 私有仓库, 改写历史风险低. 用户明确判定 v1.4.0 方案不行, 不留痕迹最干净.

### 2. 为什么不删 v1.0.0 / v1.1.0 tag?

它们已经指向正确的 commit (d286d93 / b02b9a4), 删了重建没意义. 直接留.

### 3. v1.3.1.1 tag 指向 c4d8b08, 不指向 main HEAD (fc81013)

按 git tag 规范: tag 标记 release commit 的代码状态.
- v1.3.1.1 tag → c4d8b08 (v1.3.1.1 cascade modal 修复, 真正的 release commit)
- main HEAD = fc81013 = c4d8b08 + 1 个回滚 changelog commit (元数据, 不影响代码)

**不一致** = 1 个回滚 changelog commit. 这是规范的, 不需要用 `git tag -f` 强移.

### 4. 为什么删 SUPPORTED-PROTOCOLS.md (fc1857b 删过)?

c4d8b08 状态本来就有 SUPPORTED-PROTOCOLS.md. reset --hard c4d8b08 = 它又回来. 但 fc1857b 的 commit "chore: 删除 SUPPORTED-PROTOCOLS.md (不再需要, 用户确认)" 表达的用户意图 = 不需要这个文件. 重新删, 恢复用户意图.

## 经验 (给下个 agent)

- **回滚前必看 GitHub 真实状态** — 不要凭本机 git log 决策, 用 `git ls-remote` 或 `web_fetch` API 看远程. 本机可能落后/领先远程, 凭本机做 force-push 决策容易错
- **force-push 之前先 backup** — `git checkout -b backup-<date> && git add -A && git commit` 把工作区存到独立分支, 防止 reset --hard 丢东西
- **git proxy 故障时用 inline config** — `git -c http.proxy= -c https.proxy= <cmd>` 绕开全局代理, 适合代理挂掉但 HTTPS 直连通的场景
- **force-with-lease 在 reset 后会拒绝 push** (stale info) — reset 后 lease 失效, 此时用 `--force` (私有仓库 OK)
- **回滚事件按 CHANGELOG.md 工作流要写子文件** — 跟普通 commit 一样, force-push 改 main 状态也要留 changelog 记录
- **回滚到含已删文件的 commit 时, working tree 会重新出现** — c4d8b08 状态含 SUPPORTED-PROTOCOLS.md, reset 后又出来. 跟原 commit 意图不一致时, 单独 commit 删
- **tag 标记 release commit, 不跟随后续文档 commit** — v1.3.1.1 tag → c4d8b08, main HEAD = fc81013 (c4d8b08 + 1 文档 commit), 差异是元数据, 不强移 tag
- **根 README 只做项目介绍, 技术细节归 docs/** — 别让 README 干 4 件事, 砍 73% 之后更清晰
